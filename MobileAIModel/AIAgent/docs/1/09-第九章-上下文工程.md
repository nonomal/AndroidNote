# 第九章 上下文工程

## 一句话总结

模型的上下文窗口就像一张**寸土寸金的办公桌**:系统提示词、工具说明、记忆、检索资料、对话历史全都想挤上来,而桌面就那么大。**上下文工程(Context Engineering)**研究的就是"每一轮该往桌上摆什么、摆多少、按什么顺序摆"——它是提示工程的升级版,也是长程智能体能不能跑住的分水岭。

## 本章你能学到什么

- 上下文工程和提示工程的区别,以及长任务智能体离开它为什么必翻车
- **上下文腐蚀(context rot)**:窗口标了 200K 不等于能用满 200K,而且失效方式是**性能梯度**而不是悬崖式崩溃——为什么会这样,三个技术原因说清楚
- **上下文解剖学**:系统提示词的两极误区与"最小必要信息集"、工具集怎么裁剪成 **MVTS(最小可行工具集)**、少样本示例怎么挑
- **JIT 上下文与渐进式披露**:为什么"轻量化引用 + 现场去读"比"全量预载"更好,以及为什么**混合策略才是实战答案**
- **长程任务三件套**:Compaction(压缩重启)、结构化笔记、Sub-agent 架构
- **三个完全离线、零依赖的实验**:GSSC 四阶段流水线、NoteTool、TerminalTool 的四层安全防护——最后一个还会让你**亲手戳穿自己写的白名单**
- 八个踩坑与解法,含一条必须知道的安全真相

## 一、什么是上下文工程

### 1.1 从"写好一句话"到"管好一桌子"

**提示工程**关心的是:一段提示词怎么措辞效果最好——这是"写作技巧"。
**上下文工程**关心的是:模型每次推理时,它眼前的**全部内容**(系统提示词 + 工具说明 + 记忆 + 检索结果 + 历史 + 当前问题)如何组合最优——这是"信息架构"。

为什么这事越来越重要?因为智能体的上下文来源爆炸了。一个真实智能体每轮要塞的东西:

```
┌── 上下文窗口(比如 32K Token)───────┐
│ 系统提示词(人设+规则)      ~800 tok │ ← 固定开销
│ 工具说明书(20个工具)      ~3000 tok │ ← 固定开销
│ 记忆检索结果               ~1000 tok │ ← 动态
│ RAG 检索的文档块           ~4000 tok │ ← 动态
│ 历史对话(已聊50轮)       ~20000 tok │ ← 疯狂膨胀!
│ 当前用户问题                ~200 tok │
└──────────────────────────────────┘
```

不管理的下场:历史把窗口挤爆 → 要么报错,要么框架默默截断最早的内容 → **系统提示词或关键事实被挤出去** → 智能体突然"性情大变"或忘了任务目标。docs/2 第 16 篇坑 7"上下文溢出"讲的就是这个事故现场。

### 1.2 上下文腐蚀:200K 的窗口不等于 200K 的能力

这是本章最重要、也最容易被误传的一个概念。

**是什么**:随着上下文里塞的内容越来越多,模型**准确回忆其中信息的能力会持续下降**。这个现象叫**上下文腐蚀(context rot)**。厂商标称的"支持 200K 上下文"说的是**技术上不报错**,不是"塞满 200K 时效果和塞 2K 一样好"。

**为什么会这样**,三个原因:

1. **注意力被拉薄**。Transformer 的注意力机制要计算每个 token 和其他所有 token 的两两关系,token 数量翻倍,关系对数量涨到四倍($n^2$)。但模型的"注意力总量"是有限的——内容越多,分给每一条的注意力就越少。就像一个人同时听 100 个人说话,不是听不见,是听不清。
2. **训练数据的长度分布是偏的**。互联网上的文本绝大多数是短的,几十万字的超长样本极少。所以模型在长上下文上的训练远不如短上下文充分——**它在长文里的表现是"外推",不是"内插"**。
3. **位置编码要做插值**。模型原本在比如 4K 长度上训练位置编码,扩展到 128K 时要把位置刻度"拉长"(插值)。副作用是**位置精度被牺牲**:模型知道某句话大概在前半段,但"到底是第 300 句还是第 320 句"变模糊了。

**最关键的一点,请务必记住**:上下文腐蚀表现为**平滑的性能梯度**,不是悬崖式崩溃。

> 这一点为什么重要?因为**悬崖式崩溃你会立刻发现,性能梯度你不会**。塞到 60% 满的时候,模型不会报错、不会胡言乱语,只是回答质量悄悄降了一点——降到什么程度你没有基准可比。**这是最危险的失效模式:没有报警,只有慢慢变差。**

> 顺便纠正一个常见误传:很多资料会说"模型对开头和结尾最敏感,中间容易被忽略"(Lost in the Middle)。那是关于**特定位置**的另一个研究结论,和这里讲的**随长度整体退化**是两回事。本章讲的机制是上下文腐蚀。**面试时把两者混着说,是会被追问出来的。**

**怎么用这个认知**:一条实操准则——**别用"能塞进窗口"作为设计目标,用"能塞进窗口的一半"**。以及:任何时候你觉得"反正窗口够大,全塞进去吧",都要停下来想一下这条梯度。

### 1.3 三条黄金原则

1. **预算制**:给每类内容分配 Token 配额(如系统 5%、工具 10%、检索 20%、历史 50%、留白 15%),超配额就压缩,谁也不许挤占别人;
2. **新鲜与重要优先**:历史太长时,**保最近几轮原文 + 更早的压缩成摘要**;检索结果按相关度截断;
3. **少而准胜过多而全**:因为有上下文腐蚀,**塞进去的每一条都要为自己的位置付费**。判断标准不是"这条有没有用",而是"这条的价值是否超过它挤薄其他内容的代价"。

## 二、上下文解剖学:每个部件怎么摆

一个完整的上下文分成几个部件,每个部件都有各自的常见错法。

### 2.1 系统提示词:两极误区

系统提示词是最容易写坏的部件,而且坏在**两个相反的方向**上:

| 误区 | 长什么样 | 后果 |
|---|---|---|
| **过度硬编码** | 把几十种情况写成 `如果用户问A就回答B;如果问C就…` 的 if-else 清单 | 变成脆弱的规则引擎。用户一问清单外的情况就懵;而且清单越长,模型越倾向于机械匹配而不是理解 |
| **过于空泛** | "你是一个专业、友好、乐于助人的助手" | 等于没说。模型没有得到任何可执行的判断依据 |

**正确的落点叫"最小必要信息集"**:提供足够的信号让模型做出正确判断,但不要多。

> 名词补课——**"最小"不等于"最短"**。这是最容易理解错的地方。如果一条关键约束(比如"退款金额超过 500 元必须转人工")不写清楚,模型必然做错——那这条就是**必要**的,再长也得写。反过来,一段华丽的人设描写不影响任何判断,再短也是冗余。**判断标准是"删掉它模型会不会做错",不是字数。**

结构上的实操建议:**用分区组织**。把系统提示词切成 `[角色]` `[能力边界]` `[输出格式]` `[禁止事项]` 几块,而不是写成一大段。分区的好处是:你自己改的时候知道改哪儿,模型读的时候也有结构线索。

### 2.2 工具说明:裁剪出 MVTS

工具说明书是**固定开销里最容易失控的一块**——20 个工具的 JSON Schema 轻松吃掉 3000 token,而且每一轮都要重付一次。

三条原则:

1. **Token 友好**:描述写清楚意图就停,不要把参数的每种取值都罗列一遍。
2. **职责单一、低重叠**:两个功能重叠的工具比一个都没有更糟——模型会在它们之间反复摇摆,或者随机挑一个。
3. **别攒臃肿工具集**,要主动裁剪出 **MVTS(最小可行工具集)**。

> 名词补课——**MVTS(Minimum Viable Tool Set,最小可行工具集)**:能覆盖目标任务的最小工具集合。裁剪的检验方法很简单——**逐个把工具拿掉,看任务还能不能完成**。拿掉之后照样能完成的,就该删。
>
> 为什么要这么狠?因为工具集变大有两重代价:①**每轮固定 token 开销**;②更隐蔽的一重——**选择困难**。工具从 5 个涨到 30 个,模型选错的概率不是线性上升,而是明显加速。

### 2.3 少样本示例:多样且典型

给示例(few-shot)几乎总是有效,但挑示例有讲究:**要多样且典型,不要凑数量**。

- **典型**:每个示例代表一类真实会遇到的情况,而不是你随手编的。
- **多样**:三个示例应该覆盖三种不同情形(正常情况、边界情况、需要拒绝的情况),而不是同一种情形的三个变体。

> 一个高频错法:塞五个几乎一样的示例,以为"强化了模式"。实际效果是模型学会了那一种情形的模板,遇到第二种情形就套用错模板。**三个多样的示例胜过十个同质的。**

## 三、JIT 上下文与渐进式披露

### 3.1 是什么

**JIT 上下文(Just-In-Time Context,即时上下文)**:不预先把资料全部塞进上下文,而是在上下文里只放**轻量化引用**(文件路径、数据库 ID、URL),等真正需要时再现场去读。

这和你自己工作的方式一模一样:你不会把整个代码库背下来,你记的是"配置在 `config/settings.py` 里",要用的时候打开看。

**渐进式披露(Progressive Disclosure)**:每次探索只揭开一层。先 `ls` 看目录结构 → 决定进哪个目录 → 再 `ls` → 找到目标文件 → 才 `cat` 内容。**每一步的观察结果都为下一步提供决策依据**,这样上下文里累积的都是"路上真正需要的",而不是"可能有用的一大堆"。

### 3.2 一个反直觉的收获:元数据本身就携带语义

这是 JIT 思路里最容易被忽略的红利。看这两个路径:

```
tests/test_utils.py          ← 一眼看出:这是测试文件
src/core/test_utils.py       ← 一眼看出:这是核心代码里的一个工具模块,名字里带 test 但不是测试
```

**文件名、目录层级、命名约定、修改时间——这些元数据不占什么 token,但携带了大量语义信息。** 智能体读到 `ls` 的输出时,其实已经获得了远超"文件名列表"的信息:项目结构、模块划分、哪个目录是最近在改的。这是"轻量化引用"比"全量预载"更聪明的深层原因——**引用不只是省 token,它还自带结构信息**。

### 3.3 但混合策略才是实战答案

**这一节请特别注意,因为很多资料在这里给了片面结论。**

JIT 不是"唯一正解"。纯 JIT 的代价是:每次探索都是一轮额外的模型调用 + 工具执行,**慢且贵**,而且模型可能在探索上绕远路。

**实战中更有效的是混合策略**:

| 内容类型 | 策略 | 例子 |
|---|---|---|
| **稳定、高频、必读** | **预加载** | 项目的 README、编码规范、API 约定 |
| **量大、只用一小部分** | **JIT** | 代码库文件内容、日志、数据库记录 |

一句话:**把"地图"预先给它,把"具体地块"留给它自己去看**。所以你既要在系统提示词里放 README 和规范,也要给它 `glob`/`grep`/`read_file` 这类工具。Claude Code、Cursor 这类编程智能体走的都是这条混合路线。

### 4.1 实验一:GSSC 四阶段上下文流水线

**GSSC** 是上下文组装的四个阶段:**Gather(汇集)→ Select(选择)→ Structure(结构化)→ Compress(压缩)**。

| 阶段 | 干什么 | 关键决策 |
|---|---|---|
| **Gather** | 把所有可能有用的信息包成统一格式的候选 | 每个来源独立 try/except,一个源挂了不能拖垮整条流水线 |
| **Select** | 给每个候选打分,在预算内贪心装包 | 打分公式怎么配、预算怎么留白 |
| **Structure** | 按固定分区拼装成最终文本 | 分区顺序 |
| **Compress** | 万一还是超了,按分区截断兜底 | 截在哪、怎么标记 |

新建 `ctx_builder.py`,逐段敲入。

**第 1 段:Token 估算 + 候选信息包**

```python
"""实验一:手写 GSSC 上下文流水线(Gather-Select-Structure-Compress)。"""
import math
from dataclasses import dataclass, field
from datetime import datetime, timedelta
from typing import Any, Dict, List, Optional


def count_tokens(text: str) -> int:
    """估算 Token:中文 1 字 ≈ 1 token,英文 1 单词 ≈ 1.3 token。
    生产环境换成 tiktoken,接口不变。"""
    chinese = sum(1 for ch in text if "一" <= ch <= "鿿")
    words = len([w for w in text.split() if w])
    return int(chinese + words * 1.3)


@dataclass
class ContextPacket:
    """候选信息包:一切要进上下文的东西都先包成这个"""
    content: str
    timestamp: datetime
    relevance_score: float = 0.5          # 0.5 是"还没算过"的哨兵值
    metadata: Dict[str, Any] = field(default_factory=dict)
    token_count: int = 0

    def __post_init__(self):
        if not self.token_count:
            self.token_count = count_tokens(self.content)
        self.relevance_score = max(0.0, min(1.0, self.relevance_score))
```

> 名词补课——**`@dataclass`**:Python 的一个装饰器,加在类上面,它会自动帮你生成 `__init__` 等样板方法。你只需要声明"这个类有哪些字段、默认值是什么",不用手写 `def __init__(self, content, timestamp, ...): self.content = content` 那一长串。
>
> **`__post_init__`**:`@dataclass` 提供的钩子,在字段都赋值完之后自动调用。这里用它做两件事:没算过 token 就现算;把相关性夹到 0~1 之间(`max(0.0, min(1.0, x))` 是"夹紧"的标准写法)。
>
> **`field(default_factory=dict)`**:字典这种可变类型不能直接写 `= {}` 当默认值(那样所有实例会共享同一个字典,是 Python 的经典坑),必须用 `default_factory` 告诉它"每次新建实例时调用 `dict()` 造一个新的"。
>
> **哨兵值(sentinel)**:`relevance_score = 0.5` 这个默认值不是"相关性中等"的意思,而是"**还没算过**"的标记。后面 Select 阶段看到 0.5 就知道该现场算一次。用一个特殊取值表示"未设置"的手法就叫哨兵。

**第 2 段:配置 + 那条必须成立的断言**

```python
@dataclass
class ContextConfig:
    max_tokens: int = 300
    reserve_ratio: float = 0.2            # 给系统指令预留的比例
    min_relevance: float = 0.02           # 相关性低于此值直接丢弃
    recency_weight: float = 0.3
    relevance_weight: float = 0.7
    enable_compression: bool = True

    def __post_init__(self):
        assert abs(self.recency_weight + self.relevance_weight - 1.0) < 1e-6, \
            "两个权重必须加起来等于 1.0"
```

> 为什么要有这句 `assert`?因为两个权重加起来必须是 1.0,最终得分才落在 0~1 这个可解释的区间里。如果你手滑写成 0.7 和 0.5,程序不会报错,只会给出一堆你无法解读的分数——**这种 bug 最难查**。所以宁可在构造时就崩掉。`abs(x - 1.0) < 1e-6` 而不是 `x == 1.0`,是因为浮点数有微小误差(`0.3 + 0.7` 在计算机里不严格等于 `1.0`)。

**第 3 段:G——汇集**

```python
class ContextBuilder:
    def __init__(self, config: Optional[ContextConfig] = None):
        self.config = config or ContextConfig()

    # ---------- G:汇集 ----------
    def _gather(self, system: str, history: List[str],
                knowledge: List[str], notes: List[str]) -> List[ContextPacket]:
        packets, now = [], datetime.now()
        packets.append(ContextPacket(system, now, relevance_score=1.0,
                                     metadata={"type": "system_instruction"}))
        for i, h in enumerate(history):                     # 越靠后越新
            age = timedelta(hours=(len(history) - i) * 20)
            packets.append(ContextPacket(h, now - age,
                                         metadata={"type": "history"}))
        for k in knowledge:
            packets.append(ContextPacket(k, now, metadata={"type": "knowledge"}))
        for n in notes:
            packets.append(ContextPacket(n, now - timedelta(hours=5),
                                         relevance_score=0.7,
                                         metadata={"type": "note"}))
        print(f"[Gather] 汇集了 {len(packets)} 个候选信息包")
        return packets
```

注意两个细节:系统指令的相关性**直接写死 1.0**(它永远最重要,不参与打分);笔记给 0.7 的**先验分**(是智能体自己认为值得记的,起点应该高于普通历史)。

> 生产版本里,每个来源的读取都要单独包一层 `try/except`——记忆库连不上、笔记文件被删,都不能让整条流水线崩掉,而应该少一个来源继续跑。

**第 4 段:S——选择(打分 + 贪心装包)**

```python
    # ---------- S:选择 ----------
    @staticmethod
    def _relevance(content: str, query: str) -> float:
        """Jaccard 相似度。中文按字切,英文按词切(简版)"""
        def toks(s):
            return set(ch for ch in s if "一" <= ch <= "鿿") | set(s.lower().split())
        c, q = toks(content), toks(query)
        return len(c & q) / len(c | q) if (c | q) else 0.0

    @staticmethod
    def _recency(ts: datetime) -> float:
        """指数衰减:越旧分越低,地板 0.1"""
        age_hours = (datetime.now() - ts).total_seconds() / 3600
        return max(0.1, min(1.0, math.exp(-0.1 * age_hours / 24)))
```

> 名词补课——**Jaccard 相似度**:两个集合的**交集大小 ÷ 并集大小**。中文写法是"共同词占全部词的比例"。比如"故宫门票"和"故宫闭馆"的字集合分别是 `{故,宫,门,票}` 和 `{故,宫,闭,馆}`,交集 2 个字,并集 6 个字,相似度 2/6 ≈ 0.33。
>
> `c & q` 是集合的交集,`c | q` 是并集——这是 Python 集合(`set`)的运算符,不是逻辑与或。
>
> **为什么用 Jaccard 而不是第八章的余弦相似度**?因为 Jaccard 是纯字面匹配,**零依赖、可手算、结果可预测**,适合教学。生产环境换成向量的余弦相似度,能匹配"故宫"和"紫禁城"这种同义表达——但接口不变,只需要替换这一个函数。
>
> **指数衰减 `math.exp(-0.1 * age_hours / 24)`**:`age_hours/24` 是过了几天,乘上 -0.1 再取指数。效果是刚才发生的接近 1.0,一天前 ≈ 0.90,一周前 ≈ 0.50,一个月前 ≈ 0.05。**为什么要用 `max(0.1, ...)` 设一个地板**?因为再老的信息也不该被判为"完全无价值"——它的相关性分应该由内容决定,不该被时间归零。

```python
    def _select(self, packets, query, available):
        cfg = self.config
        sys_p = [p for p in packets if p.metadata.get("type") == "system_instruction"]
        others = [p for p in packets if p.metadata.get("type") != "system_instruction"]
        used = sum(p.token_count for p in sys_p)
        if used >= available:
            print("[Select] ⚠️ 系统指令已占满预算,其余全部放弃")
            return sys_p

        scored, filtered = [], []
        for p in others:
            if p.relevance_score == 0.5:                    # 哨兵:现算
                p.relevance_score = self._relevance(p.content, query)
            score = (cfg.relevance_weight * p.relevance_score
                     + cfg.recency_weight * self._recency(p.timestamp))
            if p.relevance_score >= cfg.min_relevance:
                scored.append((score, p))
            else:
                filtered.append(p)
        scored.sort(key=lambda x: x[0], reverse=True)

        selected, dropped = list(sys_p), []
        for score, p in scored:                             # 贪心装包
            if used + p.token_count <= available:
                selected.append(p)
                used += p.token_count
            else:
                dropped.append(p)
        for p in filtered:
            print(f"[Select] ✂ 相关性过低被过滤({p.relevance_score:.3f}):"
                  f"{p.content[:22]}")
        for p in dropped:
            print(f"[Select] ✂ 预算不足被丢弃:{p.content[:22]}")
        print(f"[Select] 打分后入选 {len(selected)} 个 / 落选 "
              f"{len(filtered) + len(dropped)} 个,占用 {used} tokens"
              f"(上限 {available})")
        return selected
```

三个要点:

- **系统指令走单独通道**,先扣掉它的 token,剩下的才拿去竞争。如果系统指令本身就超了预算,直接返回——这是最坏情况的兜底。
- **两种落选是两回事**,所以分别打印:`相关性过低被过滤`(内容不相关,再有预算也不要)和 `预算不足被丢弃`(相关但桌子满了)。**调优时这两条日志指向完全不同的动作**:前者说明你的相关性阈值或匹配算法要调,后者说明你的预算或压缩策略要调。
- **贪心装包**:按分数从高到低排,能装下就装,装不下就跳过继续试下一个(注意不是 `break`——后面可能有更小的能塞进缝里)。这是背包问题的贪心近似解,不保证最优但足够好且极快。

**第 5 段:S——结构化(注意分区顺序)**

```python
    # ---------- S:结构化 ----------
    def _structure(self, selected, query):
        role, evidence, context = [], [], []
        for p in selected:
            t = p.metadata.get("type", "general")
            if t == "system_instruction":
                role.append(p.content)
            elif t in ("knowledge", "rag_result"):
                evidence.append(p.content)
            else:
                context.append(p.content)
        secs = []
        if role:
            secs.append("[Role & Policies]\n" + "\n".join(role))
        secs.append(f"[Task]\n{query}")                     # 任务放第二位,不是压轴
        if evidence:
            secs.append("[Evidence]\n" + "\n---\n".join(evidence))
        if context:
            secs.append("[Context]\n" + "\n".join(context))
        secs.append("[Output]\n请基于以上信息,提供准确、有据的回答。")
        return "\n\n".join(secs)
```

**这里有一个反直觉的设计,请特别注意:`[Task]` 放在第二位,紧跟角色之后,而不是压轴放最后。**

为什么?因为**先说清"要干什么",后面的资料才有被正确使用的框架**。如果任务放最后,模型是"先读了一堆资料,然后才知道要干嘛"——它在读资料时没有筛选依据。把任务提前,相当于先给模型一副眼镜,再让它看资料。

分区顺序最终是:`[Role & Policies]` → `[Task]` → `[Evidence]` → `[Context]` → `[Output]`。最后那个 `[Output]` 分区是**输出指令**,它才是压轴的——因为那是"现在开始动手"的发令枪。

> 顺便说一句:`[Evidence]` 里的多条资料用 `\n---\n` 隔开,而不是直接换行。**这个分隔符很重要**——它让模型能看出"这是三份独立的资料",而不是一段连续的长文。引用来源时也不容易串台。

**第 6 段:C——压缩兜底**

```python
    # ---------- C:压缩 ----------
    def _compress(self, ctx, limit):
        cur = count_tokens(ctx)
        if cur <= limit:
            return ctx
        print(f"[Compress] 超限({cur} > {limit}),按分区截断")
        out, total = [], 0
        for sec in ctx.split("\n\n"):
            st = count_tokens(sec)
            if total + st <= limit:
                out.append(sec)
                total += st
            else:
                left = limit - total
                if left > 20:
                    ratio = len(sec) / max(st, 1)
                    out.append(sec[:int(left * ratio)] + "\n[... 内容已压缩 ...]")
                break
        result = "\n\n".join(out)
        print(f"[Compress] {cur} -> {count_tokens(result)} tokens")
        return result

    def build(self, system, query, history=(), knowledge=(), notes=()):
        cfg = self.config
        available = int(cfg.max_tokens * (1 - cfg.reserve_ratio))
        print(f"\n=== 预算:窗口 {cfg.max_tokens},留白 {cfg.reserve_ratio:.0%},"
              f"可用 {available} tokens ===")
        packets = self._gather(system, list(history), list(knowledge), list(notes))
        selected = self._select(packets, query, available)
        ctx = self._structure(selected, query)
        if cfg.enable_compression:
            ctx = self._compress(ctx, cfg.max_tokens)
        return ctx
```

> **`if left > 20` 这个判断是干什么的?** 如果剩余预算只有 5 个 token,截出来的那点碎片对模型毫无用处,反而是噪音——干脆整段不要。**宁可少一段完整的,不要多一段残缺的。**
>
> `[... 内容已压缩 ...]` 这个标记也不是装饰:它明确告诉模型"这里有东西被截掉了",模型就不会把残句当成完整信息去推理。**截断必须留痕**,这是一条通用工程规矩。

### 4.2 实验二:NoteTool——把状态从上下文卸载到磁盘

上下文再怎么精打细算,窗口终究有限。跑几小时的**长程智能体**(比如"把这个代码库的所有注释翻译成英文")需要把信息**外置**到窗口之外。

**NoteTool 是什么**:给智能体一本工作笔记。**上下文里只放"当前在干嘛",全局进度放笔记里。** 这和你工作时开个备忘录是同一个道理。

设计上有三个要点,每一个都对应一条实操教训:

| 设计 | 为什么 |
|---|---|
| **Markdown + YAML 前置元数据** | 笔记要**人机都能读**。Markdown 人能直接看,YAML 头让程序能解析类型/标签/时间 |
| **单独的索引文件 `notes_index.json`** | 检索时不用打开所有笔记文件。索引里存标题、类型、预览,足够做初筛 |
| **单一入口 `run({"action": ...})`** | 工具暴露给 LLM 时只需要**一个** JSON Schema,而不是七个。直接省下大把固定开销(回想 2.2 节的 MVTS) |

**笔记类型是一个受控词表**,不是随便填的字符串:

| 类型 | 装什么 |
|---|---|
| `task_state` | 当前进度("模块B剩3个文件") |
| `conclusion` | 已经确定的结论("统一用 Google docstring") |
| `blocker` | 卡住的问题("legacy 目录是 GBK 编码") |
| `action` | 待办事项 |
| `reference` | 外部参考(链接、文档位置) |
| `general` | 其他 |

> **为什么要限定类型?** 因为检索时经常需要"只看当前进度"或"只看卡点"。如果类型是自由文本,模型这次写 `progress` 下次写 `task_progress`,过滤就失效了。**受控词表 + 传错就报错**,这是让 LLM 产出结构化数据的最有效手段。

新建 `note_tool.py`。

**第 1 段:骨架 + 索引读写**

```python
"""实验二:手写 NoteTool(结构化笔记),把状态从上下文卸载到磁盘。"""
import json
import os
from datetime import datetime
from typing import Any, Dict, List

NOTE_TYPES = ("task_state", "conclusion", "blocker", "action", "reference", "general")


class NoteTool:
    def __init__(self, workspace: str = "./notes"):
        self.workspace = workspace
        os.makedirs(self.workspace, exist_ok=True)
        self.index_path = os.path.join(self.workspace, "notes_index.json")
        self.index: List[Dict[str, Any]] = self._load_index()

    def _load_index(self):
        if os.path.exists(self.index_path):
            with open(self.index_path, encoding="utf-8") as f:
                return json.load(f)
        return []

    def _save_index(self):
        with open(self.index_path, "w", encoding="utf-8") as f:
            json.dump(self.index, f, ensure_ascii=False, indent=2)

    @staticmethod
    def _build_markdown(meta: Dict[str, Any], content: str) -> str:
        header = "".join(f"{k}: {v}\n" for k, v in meta.items())
        return f"---\n{header}---\n\n{content}"
```

> `os.makedirs(..., exist_ok=True)`:创建目录,已存在就不报错。少了 `exist_ok=True`,第二次运行就崩。
>
> `json.dump(..., ensure_ascii=False)`:不加这个参数,中文会被存成 `模块` 这样的转义码——文件还是能读,但人打开看是一堆乱码。**凡是写中文 JSON 都要加。**
>
> `_build_markdown` 生成的就是标准的 YAML 前置元数据格式:三个减号开头、键值对、三个减号收尾、空行、正文。GitHub、各种静态博客都认这个格式。

**第 2 段:create / read / update**

```python
    def _create(self, title, content, note_type="general", tags=()):
        if note_type not in NOTE_TYPES:
            return {"ok": False, "error": f"未知类型 {note_type},可选:{NOTE_TYPES}"}
        note_id = f"note_{datetime.now():%Y%m%d_%H%M%S}_{len(self.index)}"
        meta = {"id": note_id, "title": title, "type": note_type,
                "tags": ",".join(tags), "created": f"{datetime.now():%Y-%m-%d %H:%M:%S}"}
        path = os.path.join(self.workspace, note_id + ".md")
        with open(path, "w", encoding="utf-8") as f:
            f.write(self._build_markdown(meta, content))
        self.index.append({**meta, "path": path, "preview": content[:40]})
        self._save_index()
        return {"ok": True, "id": note_id}

    def _read(self, note_id):
        for it in self.index:
            if it["id"] == note_id:
                with open(it["path"], encoding="utf-8") as f:
                    return {"ok": True, "content": f.read()}
        return {"ok": False, "error": f"找不到笔记 {note_id}"}

    def _update(self, note_id, content):
        for it in self.index:
            if it["id"] == note_id:
                meta = {k: it[k] for k in ("id", "title", "type", "tags", "created")}
                meta["updated"] = f"{datetime.now():%Y-%m-%d %H:%M:%S}"
                with open(it["path"], "w", encoding="utf-8") as f:
                    f.write(self._build_markdown(meta, content))
                it["preview"] = content[:40]
                self._save_index()
                return {"ok": True, "id": note_id}
        return {"ok": False, "error": f"找不到笔记 {note_id}"}
```

> **ID 为什么是 `note_20260816_111131_0` 这种格式?** 时间戳 + 序号。光有时间戳的话,同一秒内创建两条会撞车(智能体连续记两条笔记完全正常);光有序号则看不出时间。**两者拼起来既唯一又可读。**
>
> `f"{datetime.now():%Y%m%d_%H%M%S}"` 是 f-string 里的格式化写法,等价于 `datetime.now().strftime("%Y%m%d_%H%M%S")`,但更短。
>
> `{**meta, "path": path, ...}` 是**字典解包合并**:把 `meta` 里所有键值倒进一个新字典,再补两个键。索引里存的是 meta 的副本 + 路径 + 预览。
>
> **`_update` 里 `created` 保留、加一个 `updated`** —— 不要覆盖创建时间。长程任务里"这条笔记从什么时候就在了"是有用信息。

**第 3 段:search / list / summary / delete**

```python
    def _search(self, keyword, note_type=None):
        hits = []
        for it in self.index:
            if note_type and it["type"] != note_type:
                continue
            with open(it["path"], encoding="utf-8") as f:
                body = f.read()
            if keyword.lower() in body.lower():
                hits.append({"id": it["id"], "title": it["title"],
                             "type": it["type"], "preview": it["preview"]})
        return {"ok": True, "count": len(hits), "results": hits}

    def _list(self, note_type=None):
        items = [it for it in self.index
                 if not note_type or it["type"] == note_type]
        return {"ok": True, "count": len(items),
                "items": [{"id": i["id"], "title": i["title"], "type": i["type"]}
                          for i in items]}

    def _summary(self):
        by_type: Dict[str, int] = {}
        for it in self.index:
            by_type[it["type"]] = by_type.get(it["type"], 0) + 1
        return {"ok": True, "total": len(self.index), "by_type": by_type}

    def _delete(self, note_id):
        for i, it in enumerate(self.index):
            if it["id"] == note_id:
                os.remove(it["path"])
                self.index.pop(i)
                self._save_index()
                return {"ok": True, "deleted": note_id}
        return {"ok": False, "error": f"找不到笔记 {note_id}"}
```

> **`_search` 返回的是预览而不是全文**,这是刻意的。搜索结果直接进上下文,如果每条都是全文,搜出五条就把窗口撑爆了。**先给预览让模型挑,挑中了再 `read` 全文**——这正是 3.1 节讲的渐进式披露,在工具内部也适用。
>
> `_summary` 用来干什么?**让智能体在长任务中"看一眼全局"而不读任何笔记内容**:总共 12 条,其中 3 个卡点、5 条进度。这是极其便宜的态势感知。

**第 4 段:唯一入口**

```python
    def run(self, params: Dict[str, Any]) -> Dict[str, Any]:
        action = params.get("action")
        table = {
            "create": lambda: self._create(params["title"], params["content"],
                                           params.get("note_type", "general"),
                                           params.get("tags", ())),
            "read": lambda: self._read(params["note_id"]),
            "update": lambda: self._update(params["note_id"], params["content"]),
            "search": lambda: self._search(params["keyword"], params.get("note_type")),
            "list": lambda: self._list(params.get("note_type")),
            "summary": lambda: self._summary(),
            "delete": lambda: self._delete(params["note_id"]),
        }
        if action not in table:
            return {"ok": False, "error": f"未知 action {action},可选:{list(table)}"}
        return table[action]()
```

> **注意这里没有 `add_note("...")` 这种方法。** 所有操作都通过 `run({"action": ...})` 一个入口进,这是刻意的设计——见上面表格第三行。
>
> `lambda:` 包一层是为了**延迟执行**:字典字面量一旦求值,所有 value 都会被计算。如果不包 lambda,`params["title"]` 在 action 是 `read` 时也会被访问,直接 `KeyError`。包成 lambda 后,只有被选中的那一个才真的执行。
>
> **未知 action 要把可选值列出来**。模型看到 `未知 action add_note,可选:['create', 'read', ...]` 能自己纠正;只回 `error` 它只能瞎猜。**给 LLM 的报错信息里要带可用选项**,这是一条通用规则。

### 4.3 实验三:TerminalTool 的四层防护,以及亲手戳穿它

**TerminalTool 是什么**:让智能体能 `ls`、`cat`、`grep`——需要哪个文件的内容,现场去读,而不是把整个代码库塞进上下文。这是 3.1 节 JIT 上下文的执行器。

**但把 shell 交给一个语言模型是本书风险最高的一件事**,所以必须有防护。四层:

| 层 | 干什么 | 挡住什么 |
|---|---|---|
| **①命令白名单** | 只允许一批只读命令 | `rm -rf /`、`curl` 外传数据、`python3 -c` 任意执行 |
| **②工作目录沙箱** | 所有操作限制在指定目录内 | `cat /etc/passwd`、`cd ../../../` 逃出去 |
| **③超时** | 单条命令最多跑 N 秒 | `find /` 这种把机器拖死的命令 |
| **④输出限流** | 输出超过 N 字节就截断 | `cat` 一个 2GB 的日志把上下文和内存一起打爆 |

新建 `terminal_tool.py`。

**第 1 段:白名单与四个参数**

```python
"""实验三:手写 TerminalTool 的四层安全防护,并亲手戳穿它。"""
import os
import subprocess
from pathlib import Path

ALLOWED = {
    "ls", "dir", "tree", "cat", "head", "tail", "less", "more",
    "find", "grep", "egrep", "fgrep", "wc", "sort", "uniq", "cut",
    "awk", "sed", "pwd", "cd", "file", "stat", "du", "df",
    "echo", "which", "whereis",
}


class TerminalTool:
    def __init__(self, workspace: str = ".", timeout: int = 30,
                 max_output_size: int = 10 * 1024 * 1024):
        self.workspace = Path(workspace).resolve()      # 第②层:沙箱根
        self.current_dir = self.workspace
        self.timeout = timeout                          # 第③层
        self.max_output_size = max_output_size          # 第④层
```

> **看清这份白名单里有什么、没有什么。** 有的全是**只读或只看**的命令。没有 `rm`、`mv`、`cp`、`chmod`、`python`、`pip`、`curl`、`wget`、`ssh`、`git`。
>
> **`Path(workspace).resolve()`** 是沙箱的地基:`.resolve()` 把路径**转成绝对路径并消解掉所有 `..` 和符号链接**。不做这一步,后面的越界检查全是纸糊的——`/tmp/x/../../etc` 字面上看着在 `/tmp/x` 底下。
>
> `max_output_size` 默认 10MB = `10 * 1024 * 1024`。写成乘法而不是 `10485760`,是为了让人一眼看出单位。

**第 2 段:第①层和第②层**

```python
    def _check_whitelist(self, command: str):
        head = command.strip().split()[0] if command.strip() else ""
        if head not in ALLOWED:
            return False, f"❌ 命令 '{head}' 不在白名单中"
        return True, ""

    def _do_cd(self, command: str):
        target = command.strip()[2:].strip() or "."
        new_dir = (self.current_dir / target).resolve()
        try:
            new_dir.relative_to(self.workspace)          # 关键一行
        except ValueError:
            return f"❌ 拒绝:{new_dir} 在工作目录 {self.workspace} 之外"
        if not new_dir.is_dir():
            return f"❌ 目录不存在:{new_dir}"
        self.current_dir = new_dir
        return f"✅ 当前目录:{self.current_dir}"
```

> **`new_dir.relative_to(self.workspace)` 是整个沙箱的核心一行。** 它问的是:"`new_dir` 能不能表示成相对于 `workspace` 的路径?"能,说明在里面;不能,`pathlib` 抛 `ValueError`,我们抓住它就知道越界了。
>
> **为什么用抛异常来做判断,而不是 `str(new_dir).startswith(str(workspace))`?** 因为字符串前缀匹配会误判:`/tmp/sandbox-evil` 的确以 `/tmp/sandbox` 开头,但它是另一个目录。`relative_to` 是按**路径段**比较的,不会犯这个错。
>
> `cd` 必须单独处理,不能丢给 `subprocess`——因为子进程 `cd` 完就退出了,父进程的目录没变。所以要自己维护 `current_dir`。

**第 3 段:执行,以及第③④层**

```python
    def run(self, command: str) -> str:
        ok, msg = self._check_whitelist(command)
        if not ok:
            return msg
        if command.strip().startswith("cd"):
            return self._do_cd(command)
        try:
            r = subprocess.run(
                command, shell=True, cwd=str(self.current_dir),
                capture_output=True, text=True,
                timeout=self.timeout,                   # 第③层
                env=os.environ.copy(),
            )
        except subprocess.TimeoutExpired:
            return f"❌ 命令超时(超过 {self.timeout} 秒)已被强制终止"
        out = (r.stdout or "") + (r.stderr or "")
        if len(out.encode()) > self.max_output_size:    # 第④层
            out = out[: self.max_output_size] + \
                  f"\n⚠️ 输出被截断(超过 {self.max_output_size} 字节)"
        return out or "(无输出)"
```

> 名词补课——**`subprocess.run`**:Python 启动一个外部程序并等它跑完的标准方式。`capture_output=True` 把它的输出抓回来(而不是直接打在屏幕上),`text=True` 让输出是字符串而不是字节串,`cwd=` 指定在哪个目录执行。
>
> **`r.stdout` 和 `r.stderr` 都要拼上**。只取 `stdout` 的话,命令报错时你会得到一个空字符串,模型完全不知道发生了什么——它会以为"成功了但没输出",然后基于这个错误认知继续走下去。**错误信息也是观察结果的一部分。**
>
> **`len(out.encode())` 而不是 `len(out)`**:限制的是字节数。一个中文字符在 UTF-8 里是 3 个字节,按字符数算会低估两三倍。
>
> **`timeout` 触发时会抛 `TimeoutExpired` 异常,必须自己抓。** 不抓的话整个智能体进程崩掉——一个命令超时不该让整个任务死掉,而应该返回一条错误观察让模型换个办法。

三个绕过手法,都通过了白名单检查(因为首个 token 分别是 `echo`):

1. **`echo hi; whoami`** —— 分号在 shell 里表示"执行完这条再执行下一条"。白名单只看了 `echo`,`whoami` 就这么执行了。输出里那个 `c` 就是当前用户名——**如果换成 `echo hi; rm -rf ~`,后果自己想。**
2. **`echo $(whoami)`** —— `$(...)` 是**命令替换**,shell 会先执行括号里的命令,把结果替换进来。同样绕过。反引号 `` `whoami` `` 是等价写法。
3. **`echo pwned > escaped.txt`** —— `>` 是重定向。白名单里全是"只读命令",但 `>` 让任何一个只读命令都能**写文件**。输出里的 `True` 是我们检查文件系统的结果:**文件真的被创建了。**

**根源在 `shell=True`。** 这个参数把整条命令字符串交给系统 shell 去解释,于是 `;` `&&` `|` `>` `$()` 反引号全部生效。而我们的白名单只检查了字符串的**第一个词**——检查的粒度和执行的粒度根本不匹配。

**那怎么办?** 按防护强度排序:

| 方案 | 强度 | 代价 |
|---|---|---|
| `shell=False` + 参数列表(`["ls", "-la"]`) | 中 | 失去管道、重定向等便利,复杂命令要自己拼 |
| 在白名单检查前**拒绝含 `; & \| > < $ \`` 的命令** | 中 | 容易漏(还有 `\n`、`$IFS` 等花样),属于打补丁 |
| **容器 + 只读挂载 + 无网络 + 非 root 用户** | 高 | 要引入 Docker 之类的依赖 |
| **只给受限的自定义工具**(`read_file(path)` / `list_dir(path)`),根本不给 shell | 最高 | 灵活性最低,但对绝大多数场景够用 |

**本书的建议**:如果你的智能体只需要"看文件",就**别给它 shell**,给 `read_file` 和 `list_dir` 两个受限工具。真的需要执行命令,上容器。**四层防护适合防"模型手滑",不适合防"有人故意注入"。**

> 还有一个容易漏的点:代码里 `env=os.environ.copy()` 把**当前进程的全部环境变量**传给了子进程——**包括你的 `OPENAI_API_KEY`**。配合上面的绕过手法,`echo hi; env` 就能把密钥打出来,而 `env` 的输出会作为观察结果进入上下文。生产环境要显式**白名单环境变量**:`env={"PATH": os.environ["PATH"], "LANG": "C.UTF-8"}`。

**改一改(必做)**:

- 把 `shell=True` 改成 `shell=False`,并把命令改成传列表 `command.split()`,重跑最后一段。三个绕过全部失效(这是实测输出):

  ```
  'echo hi; whoami'          -> 'hi; whoami\n'
  'echo $(whoami)'           -> '$(whoami)\n'
  'echo pwned > shf.txt'     -> 'pwned > shf.txt\n'
  shf.txt exists? False
  ```

  **`;`、`$()`、`>` 全都退化成普通字符,被 `echo` 原样打印出来了,文件也没被创建。** 这就是 `shell=False` 的价值:没有 shell 来解释这些符号,它们就只是字符。
- 在 `_check_whitelist` 开头加一句:`if any(c in command for c in ";&|><$`"): return False, "❌ 命令含危险字符"`,重跑。三个绕过也全部被挡。然后想想:`echo hi` 后面跟一个**真的换行符**再跟 `whoami`,能不能绕过?(能,换行在 shell 里和分号等效。**这就是"打补丁"式防护的宿命:你永远在追着新花样跑。**)

## 五、长程任务三件套

前面四节解决的是"**单次**调用怎么组织上下文"。但真实的智能体任务经常跑几十上百轮——上下文必然会满。这时候需要三种技术,它们不是三选一,而是配合使用。

| 技术 | 一句话 | 什么时候用 |
|---|---|---|
| **Compaction(压缩重启)** | 把历史提炼成高保真摘要,在**新窗口**里继续 | 单个任务本身就很长,必须连续做下去 |
| **结构化笔记** | 关键状态写到窗口外的文件里 | 任何长任务;和上面两种都能叠加 |
| **Sub-agent(子智能体)架构** | 把子任务派给拥有**干净窗口**的子智能体 | 任务能拆成相对独立的几块 |

### 5.1 Compaction:不是删,是提炼

**是什么**:当上下文快满时,让模型**总结一份高保真的交接文档**,然后**开一个新窗口**,只带着这份摘要继续干。

新手最容易做错的是"直接把前面 20 轮丢掉"。**丢掉和提炼是两回事**:丢掉会让智能体重复踩已经踩过的坑、重新做已经做过的决定;提炼后它还知道自己走过哪些路。

**摘要里必须保留什么**(这是踩出来的清单):

| 必须留 | 为什么 |
|---|---|
| **架构决策** | "我们决定用 SQLite 不用 Postgres"——丢了就会反复摇摆 |
| **未解决的 bug** | 丢了就会把已知问题当新问题重新调查一遍 |
| **实现细节** | 函数签名、字段名、文件路径——丢了下一轮就开始瞎猜 |
| **已经排除的方案** | "试过 X,不行,因为 Y"——丢了就会再试一次 X |

**可以丢的**:工具的原始输出(几十行 `ls` 结果)、失败的中间尝试的完整过程、寒暄。

**调优顺序有讲究**:**先调"召回"(该留的别漏),再调"精确度"(把冗余挤掉)。** 反过来做的后果是,你会得到一份很短但漏了关键信息的摘要,而且**漏了什么你当时看不出来**——只有在后面几十轮智能体开始犯莫名其妙的错误时才会发现。**信息漏了比摘要长了危险得多。**

> **和第八章记忆系统的关系**:Compaction 是"当前任务内"的压缩,记忆系统是"跨任务"的长期存储。一个管这次会话,一个管下次还记得。两者互补,不重复。参见 `docs/1/08` 和 `docs/2/17`。

### 5.2 结构化笔记:就是 4.2 节那个工具

**是什么**:模型在任务过程中主动把进度、结论、卡点写到磁盘,需要时再读回来。

它和 Compaction 的关键区别:**Compaction 是被动的(窗口满了才做),笔记是主动的(随时记)。** 而且笔记**跨窗口存活**——Compaction 换了新窗口,笔记文件还在那儿,新窗口第一件事就可以是 `run({"action": "summary"})` 看一眼全局。

**这两个技术叠起来才是完整方案**:

```
     ┌─────────── 窗口 1 ───────────┐
     │ 干活…干活…记笔记…干活…       │  ← NoteTool 写盘
     │ 快满了 → 生成高保真摘要      │  ← Compaction
     └──────────────┬───────────────┘
                    │  只带摘要过去
     ┌──────────────▼── 窗口 2 ─────┐
     │ 读摘要 + summary 看笔记全局   │  ← 状态没丢
     │ 干活…干活…                   │
     └──────────────────────────────┘
```

### 5.3 Sub-agent 架构:用干净窗口换隔离

**是什么**:主智能体负责规划和汇总,把具体的子任务派给**子智能体**,每个子智能体有自己**干净的上下文窗口**。

**为什么有效**——两个理由,第二个更重要:

1. **总容量变大了**:三个子智能体 = 三个窗口,能处理的信息量是单窗口的三倍。
2. **污染被隔离了**:子智能体探索时产生的一大堆中间垃圾(读了 30 个文件、试了 5 个错误方向)**留在它自己的窗口里,不会流进主窗口**。主智能体只收到结论。

**返回什么很关键**:子智能体应该返回一份 **1,000~2,000 token 的凝练摘要**,而不是把它读过的所有内容原样倒回来。如果子智能体把 30 个文件的内容全返回,主智能体的窗口照样被打爆——**那你等于什么都没隔离,只是多绕了一圈。**

**代价**:

- **Token 成本上升**。每个子智能体都要重新接收系统提示、工具定义。派五个子智能体,固定开销就交了五遍。
- **主智能体拿不到细节**。它只有摘要,如果摘要漏了关键信息,主智能体无从察觉——这和 5.1 的召回问题是同一个病。
- **不适合强耦合的子任务**。子任务 B 需要子任务 A 的中间状态时,隔离反而成了障碍。

> **判断标准**:子任务之间**能不能独立完成**?能,用 sub-agent;不能,老老实实在一个窗口里配合 Compaction。

**这张图和很多人的直觉不一样的两处,记牢**:

1. **`[Task]` 在第二位,不在最后。** 任务放前面,模型是"带着问题读材料";任务放最后,是"读完一堆材料再看要干什么"。前者更准。
2. **两种落选是两回事。** 相关性过低是"它不该来",预算不足是"它该来但挤不进"。前者说明检索有问题,后者说明预算有问题——混在一起你就不知道该改哪儿。

## 六、踩坑与专家提示

**坑 1:把"塞满窗口"当成目标。**
128K 的窗口不代表你该用 128K。**上下文腐蚀是平滑退化,没有报警**:你的智能体不会崩,只会慢慢变笨,而你以为是"模型不行"。设计目标定在**窗口的一半**,给自己留腐蚀余量。

**坑 2:把上下文腐蚀说成 "Lost in the Middle"。**
两回事。Lost in the Middle 讲的是**位置**效应(中间的信息容易被忽略);上下文腐蚀讲的是**长度**效应(输入越长,整体性能越低,和位置无关)。面试里说错这个,懂的人立刻能听出来。

**坑 3:工具越加越多。**
每加一个工具,固定开销(工具定义占的 token)每轮都要交,**而且模型选错工具的概率上升**。第二个代价通常比第一个大。用 **MVTS(最小可行工具集)**:逐个把工具拿掉,看任务还能不能完成——不能完成的才留下。

**坑 4:System Prompt 两极化。**
一极是把所有分支都硬编码成 if-else("如果用户说A就回B,如果说C就回D"),模型变成一个笨拙的规则引擎,遇到没写到的情况就崩;另一极是"你是一个有帮助的助手",空得没有任何约束力。**要的是"最小必要信息集":判断标准是"删掉这句,模型会不会做错"**——会,就留下;不会,就删掉。注意**"最小"不等于"最短"**,一句必要的复杂规则该写清楚就写清楚。

**坑 5:Few-shot 示例堆数量不管多样性。**
**三个覆盖不同情况的示例胜过十个同质的。** 十个都是"查天气"的示例,只会让模型以为它是个天气机器人。示例的作用是**划出行为的边界**,同质示例划不出边界。

**坑 6:以为 JIT 是唯一正解。**
纯 JIT 有代价:每次取信息都要多花一轮工具调用,而且模型可能取错。**混合策略更实用**——把小而必用的东西(README、编码规范、项目结构)预加载,把大而可能不用的(具体文件内容、日志、数据集)留给 JIT。

**坑 7:元数据被当成噪声扔掉。**
`tests/test_utils.py` 和 `src/core/test_utils.py` 文件名一样,但**路径本身携带语义**:一个是测试代码,一个是生产代码里的工具模块。给模型看文件列表时保留完整路径、修改时间、大小——**这些不是装饰,是模型的判断依据。**

**坑 8:压缩时不留痕迹。**
截断了却不告诉模型,模型会把残缺的内容当完整内容用,然后基于半句话做推理。**一定要插入 `[... 内容已压缩 ...]` 这样的标记**,让模型知道"这里有东西被拿掉了,如果需要我可以去取"。

**坑 9:Compaction 先追求短,后追求全。**
顺序错了。**先保证该留的都留下(召回),再挤冗余(精确度)。** 摘要长了只是浪费 token,摘要漏了会让智能体在后面几十轮里犯你完全看不懂的错。

**坑 10:Sub-agent 把原始内容全返回。**
子智能体读了 30 个文件,然后把 30 个文件的内容返回给主智能体——**你没有隔离任何污染,只是多花了一份固定开销。** 子智能体必须返回 1,000~2,000 token 的凝练结论。

**坑 11:笔记类型用自由文本。**
这次写 `progress`、下次写 `task_progress`、再下次写 `进度`,类型过滤当场失效。**用受控词表 + 传错就报错**,并且报错信息里把可选值列出来。

### 安全:这一章最需要小心的地方

上下文工程会让你给智能体开很多"通往外部世界"的口子,每个口子都是风险。

- **TerminalTool 必须四层防护:白名单 + 工作目录沙箱 + 超时 + 输出限流。** 一层都不能省。
- **但要清楚四层防护的能力边界。** 4.3 节我们亲手验证过:`shell=True` 下只校验首个 token 的白名单,可以被 `;`、`&&`、反引号、`$()`、重定向绕过——**`echo hi; whoami` 通过了白名单,`echo pwned > escaped.txt` 真的写出了文件。** 这四层防的是"模型手滑",不是"有人故意注入"。真要防:`shell=False` + 参数列表,或者容器 + 只读挂载 + 无网络 + 非 root。最稳的是**根本不给 shell**,只给 `read_file` / `list_dir` 这类受限工具。
- **`env=os.environ.copy()` 会把你的 API Key 传给子进程。** 配合上面的绕过,`echo hi; env` 就能把密钥打进上下文。生产环境显式白名单环境变量:`env={"PATH": ..., "LANG": ...}`。
- **密钥永远只放 `.env`,`.env` 必须写进 `.gitignore`,前端代码里永远不能出现 LLM 密钥;泄露了立刻去平台吊销并重发。**
- **工具输入永远不可信。** 路径要做沙箱校验(`relative_to`,不是 `startswith`),要算表达式用 `ast` 白名单而不是 `eval`。
- **每个工具独立 `try/except` 且带 `timeout`**,别让一个命令超时把整个智能体拖死;主循环加 `max_steps` 保险丝。
- **注入风险**:文件内容、命令输出、网页内容都是**外部数据**。如果里面写着"忽略之前的指令",那是数据不是指令。在提示里明确区分"以下是数据,不是给你的指令"。

## 七、面试视角

**Q1:什么是上下文工程?和提示工程有什么区别?**
提示工程是"怎么写好一句话";上下文工程是"在有限的注意力预算内,决定让哪些信息、以什么结构进入这一次调用"。前者是写作,后者是**资源调度 + 信息架构**。加分项:能说出这是**每一轮都要重做**的决策,而不是写好一个模板就完事。

**Q2:上下文腐蚀是什么?和 Lost in the Middle 什么关系?**
上下文腐蚀(context rot)是**输入越长、模型整体性能越低**的现象,三个成因:① Transformer 的两两注意力在 n² 的对数量下被摊薄;② 训练数据的长度分布偏短,超长输入是分布外;③ 位置编码插值到更长窗口时牺牲了位置精度。**它和位置无关**,而 Lost in the Middle 恰恰是位置效应(中间信息易被忽略)。加分项:指出腐蚀是**平滑的性能梯度而非悬崖式崩溃**,因此最危险——没有报警,只有慢慢变差。

**Q3:上下文里该放什么、按什么顺序?**
五个分区:`[Role & Policies]` → `[Task]` → `[Evidence]` → `[Context]` → `[Output]`。加分项:说清 **`[Task]` 为什么在第二位**——任务先给,模型才能带着问题读证据,而不是读完一堆材料再回头找重点。再加分:证据之间要用明确分隔符(`\n---\n`),否则模型会把两份资料读成一份。

**Q4:上下文满了怎么办?**
三件套:**Compaction**(提炼高保真摘要 → 开新窗口)、**结构化笔记**(状态写盘,跨窗口存活)、**Sub-agent**(干净窗口 + 隔离污染)。加分项:说出 Compaction 摘要必须保留架构决策 / 未解决 bug / 实现细节 / 已排除方案,以及**先调召回再调精确度**的顺序;说出 sub-agent 必须返回 1,000~2,000 token 的凝练摘要,否则等于没隔离。

**Q5:工具是不是越多越好?**
不是。两个代价:固定 token 开销每轮都交,**以及模型选错工具的概率上升**——后者通常更致命。用 MVTS:逐个移除工具看任务是否还能完成。加分项:提到工具描述要**职责单一、语义低重叠**,两个功能相近的工具会让模型反复选错。

**Q6:JIT 上下文是什么?是不是应该全用 JIT?**
JIT 是"先给轻量化引用(文件路径、查询接口),需要时再现场取内容"。**不该全用**:每次取都多一轮调用,而且模型可能取错。混合策略更实用——小而必用的预加载,大而可能不用的走 JIT。加分项:指出**元数据本身携带语义**(`tests/test_utils.py` vs `src/core/test_utils.py`),所以引用要保留完整路径而不是只给文件名。

**Q7:给智能体开 shell 有什么风险,怎么防?**
四层防护:白名单、工作目录沙箱、超时、输出限流。**加分项(这一问的分水岭)**:主动说出四层的边界——`shell=True` 下只检查首个 token 的白名单可以被 `;`、`$()`、`>` 绕过,因为**检查的粒度(第一个词)和执行的粒度(整条 shell 命令)不匹配**;沙箱要用 `relative_to` 按路径段比较而不是字符串 `startswith`;`env=os.environ.copy()` 会泄露 API Key。真方案是 `shell=False` + 参数列表,或容器隔离,或干脆只给受限工具。

**Q8:怎么衡量上下文工程做得好不好?**
不看"塞了多少",看三个:① 同样任务的**成功率**;② 达到同样成功率所需的**平均 token 数**;③ 任务变长时成功率的**衰减曲线**。加分项:指出要专门测**长输入下的表现**,因为腐蚀是平滑退化,短输入的测试集根本测不出来。

## 八、划重点

1. **上下文工程 = 在有限注意力预算内做资源调度**,而不是写一个好模板。每一轮都要重做这个决策。
2. **上下文腐蚀是长度效应,不是位置效应**;它是平滑的性能梯度,没有报警。别和 Lost in the Middle 搞混。
3. **设计目标定在窗口的一半**,不是"能塞进窗口"。
4. **最小必要信息集**:判断标准是"删掉它模型会不会做错"。"最小"不等于"最短"。
5. **`[Task]` 放第二位**,让模型带着问题读证据。证据之间用明确分隔符。
6. **两种落选要分开记账**:相关性过低(不该来)vs 预算不足(该来但挤不进)。
7. **MVTS**:工具的第二个代价——让模型更容易选错——比 token 开销更致命。
8. **混合策略胜过纯 JIT**:小而必用的预加载,大而可能不用的现取。元数据携带语义,别扔。
9. **压缩必须留痕**,`[... 内容已压缩 ...]`;**Compaction 先召回后精确度**;**Sub-agent 必须返回凝练摘要**。
10. **四层防护防的是模型手滑,不是恶意注入。** `shell=True` + 首 token 白名单是纸糊的——你已经亲手戳穿过了。要么 `shell=False`,要么上容器,要么根本不给 shell。

## 九、下一章预告

这一章解决的是"**信息怎么进上下文**"。但信息从哪儿来?第四章的工具是我们自己手写的,每个都要自己实现一遍——如果每个团队都重写一遍"读文件""查数据库",这活就没完了。

**第十章讲协议**:MCP(模型上下文协议)让工具变成**可插拔的标准件**——别人写好的服务器,你的智能体直接连上就能用;A2A 让智能体之间能互相对话;ANP 让智能体能发现彼此。本章的 TerminalTool、NoteTool 到了第十章会以另一种形态出现:不再是你代码里的一个类,而是一个独立进程提供的标准服务。

而这一章的核心思想在那里依然成立——**MCP 让你能接一百个工具,但 MVTS 告诉你不该接一百个。**
